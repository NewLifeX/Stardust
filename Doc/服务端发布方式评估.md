# StarServer / StarWeb / StarAgent 发布方式评估

> 版本：v1.0 | 日期：2026-11-24
> 适用：StarServer 3.7.2026.1124、StarWeb 3.7.2026.1124、StarAgent 3.7.2026.1124、.NET 10
> 关联：[NODE-StarAgent-多语言性能对比](NODE-StarAgent-多语言性能对比.md) | [NODE-StarAgent发布计划](NODE-StarAgent发布计划.md) | [NODE-StarAgent-AOT适配](NODE-StarAgent-AOT适配.md)

## 1. 结论

先回答最关心的三件事：

- **.NET 10 没有 NGEN。** `ngen.exe` 只属于 .NET Framework；`dotnet ngen` 不存在。.NET Core/.NET 5+ 最接近的受支持方案是发布时 `PublishReadyToRun`（R2R），不是部署后在目标机执行 NGEN。
- **JIT 部署 + 运行时优化，现实中对应的是“JIT + 动态 PGO”**：目标机安装运行时，程序以 IL 发布；运行时先快速 JIT，热方法再按动态 PGO 重编译。它没有 AOT 的反射限制，但拿不到 R2R 的首次启动收益。
- **稳态 CPU/内存最重要时，JIT 与 R2R 的差距没有启动阶段大。** 16 并发 800+800 请求的负载测试中，JIT 与 composite R2R 的稳态 CPU 在 ±10% 内，负载后的 RSS 基本相同；R2R 的主要收益是启动更快、初始内存更低。

| 组件 | 推荐 | 理由 |
|------|------|------|
| **StarAgent** | **框架依赖 R2R**（生产机已装 .NET 10） | 启动 2 倍左右、CPU 少 56%~65%、RSS 少约 10%；不限制反射/插件。AOT 仅在无外部插件且设备极弱时考虑。 |
| **StarServer** | **JIT 为主，R2R composite 作为需要频繁重启/扩容时的选项** | 稳态 CPU/内存与 R2R 基本打平；JIT 包更小、没有 R2R 版本/Windows 兼容坑。弱 CPU 机器或重启敏感场景用 composite R2R。 |
| **StarWeb** | **R2R composite（Windows 必须 composite）** | 启动/首次 CPU 收益明显（A2 33.6→24.2 s，CPU 50.8→39.8 s；10.0.0.1 7.9→6.0 s），初始 RSS 低约 10%；稳态与 JIT 接近。 |
| **StarServer/StarWeb 的 AOT** | **不推荐** | XCode 通过反射加载数据库驱动，ASP.NET Core 也依赖动态代码；AOT 需要大量保留/改写，收益不匹配。 |

> 一句话：**Agent 用 R2R，Server 默认 JIT、重启敏感再上 composite R2R，Web 用 composite R2R；不要为服务端追 AOT，也不要在 .NET 10 上找 NGEN。**

## 2. NGEN 的现状

| 事实 | 说明 |
|------|------|
| `ngen.exe` | 只存在于 .NET Framework（本机 `C:\Windows\Microsoft.NET\Framework64\v4.0.30319\ngen.exe`） |
| `dotnet ngen` | 不存在；.NET 10 没有目标机 NGEN 安装步骤 |
| 受支持的替代 | 发布时 `PublishReadyToRun=true`，由 crossgen2 生成 R2R 映像 |
| composite R2R | `PublishReadyToRunComposite=true`，把应用与依赖编译成组合映像；Windows 框架依赖模式尤其需要它 |
| 目标机 crossgen2 | 技术上可把 crossgen2 和运行时包带到目标机再编译，但版本强绑定、无官方部署流程，不能当作 NGEN 使用 |
| JIT 侧优化 | 动态 PGO 默认开启（`DOTNET_TieredPGO=1`），热方法会按运行时剖面重编译；无反射限制 |

**关于“JIT 发布、目标机 NGEN”**：这条路在 .NET 10 上没有官方支持。能做到的是：

1. 以框架依赖 JIT 发布，目标机安装运行时；
2. 依赖默认的动态 PGO 在运行中优化热路径；
3. 如果启动/重启时间不可接受，再改用发布时 R2R（composite），而不是目标机 NGEN。

## 3. 测试口径

### 3.1 机器

| 机器 | CPU/内存 | 运行时 |
|------|----------|--------|
| Windows 本机 | i9-10900K / 64 GB | .NET 10.0.15 |
| WSL | 12 vCPU / 24 GB | .NET 10.0.15 |
| 10.0.0.1 | Celeron J4125 / 7.5 GB | ASP.NET 10.0.9 |
| A2 | Cortex-A55 4C / 949 MB | ASP.NET 10.0.14 |
| sh14.newlifex.com | Xeon 8255C 2 vCPU / 1.9 GB | ASP.NET 10.0.0 |

### 3.2 变体与工作负载

- **框架依赖 JIT**：目标机安装运行时，应用程序集为 IL。
- **框架依赖 R2R**：应用程序集预编译；Linux 普通 R2R 已验证；Windows 普通 R2R 启动会 failfast，必须用 composite。
- **自包含 JIT/R2R**：用于隔离运行时版本影响，也用于 A2/Windows 的对照。
- 联合场景：StarServer 启动并响应 `/api` → StarWeb 接入它并响应 `/cube/info` → StarAgent 用 `-run -server` 登录并完成首次心跳。
- 指标：启动墙钟、启动 CPU、启动 RSS；稳定 20 s 后的 10 s CPU/RSS；Windows 额外做 16 并发、800 次 `/api` + 800 次 `/cube/info` 的负载测试。

> `-run` 是直接执行 `StartWork` 的前台模式；输入/输出重定向时保持运行，由测量程序在首次心跳日志出现后终止。没有新增 `-once`。

## 4. 启动与初始内存（框架依赖，生产口径）

单位：秒 / 秒 CPU / MB RSS；A2、sh14、10.0.0.1 为实测，Windows 的 R2R 为 composite。

| 机器 | StarServer JIT | StarServer R2R | StarWeb JIT | StarWeb R2R |
|------|----------------|----------------|-------------|-------------|
| WSL x64 | 1.78 / 1.76 / 204 | **1.10 / 1.19 / 192** | 3.16 / 4.87 / 336 | **2.12 / 3.78 / 326** |
| 10.0.0.1 | 4.32 / 4.74 / 210 | **2.99 / 3.38 / 191** | 7.93 / 10.95 / 355 | **6.00 / 8.45 / 320** |
| A2 arm64 | 15.40 / 20.03 / 216 | **10.55 / 13.36 / 187** | 33.61 / 50.82 / 340 | **24.20 / 39.79 / 299** |
| sh14 x64 | 5.62 / 3.20 / 200 | **1.89 / 1.86 / 187** | 8.14 / 7.78 / 453 | **4.59 / 5.06 / 289** |
| Windows | 2.34 / 2.25 / 168 | **2.28 / 2.38 / 155** | 3.82 / 5.63 / 264 | **2.53 / 5.16 / 272** |

- **弱 CPU 受益最大**：A2 上 Server 启动 15.4→10.5 s（-32%）、Web 33.6→24.2 s（-28%）；10.0.0.1 和 sh14 也明显。
- **Windows 普通框架依赖 R2R 不可用**：`dotnet StarServer.dll` 直接退出（-1073740286，无输出）；composite R2R 正常。因此 Windows 要用 R2R 就选 composite。
- **框架依赖 JIT 比自包含 JIT 快很多**：Windows Server 2.34 s vs 自包含 JIT 6.49 s；因为共享框架本身已是 R2R。生产机装运行时时，不要把自包含 JIT 的数据当成 JIT 的真实表现。

## 5. 稳定工作后的 CPU 与内存

### 5.1 Windows 负载测试

16 个并发任务，各 50 次请求，Server 打 `/api`、Web 打 `/cube/info`；数值为整轮负载期间的进程 CPU 时间。

| 形态 | Server CPU | Web CPU | 负载耗时 |
|------|-----------:|--------:|---------:|
| 框架依赖 JIT | **1.53 s** | **5.03 s** | 4.96 s |
| composite R2R（框架依赖） | 1.56 s | 5.19 s | 4.84 s |
| 自包含 R2R | 1.45 s | 4.84 s | 5.19 s |
| 自包含 JIT | 1.75 s | 5.38 s | 5.43 s |

**结论**：稳态 CPU 上 JIT 与 R2R 的差距在 ±10% 内，框架依赖 JIT 甚至略好于 composite R2R。R2R 的 CPU 优势集中在启动/首次执行，不是持续工作阶段。

负载后的 RSS：JIT Server 233 MB、composite R2R Server 233 MB；JIT Web 339 MB、composite R2R Web 339 MB。**R2R 的低内存主要体现在启动/初始阶段，负载后趋同。**

### 5.2 Agent 稳态

| 机器 | JIT 启动 / CPU / RSS | R2R 启动 / CPU / RSS |
|------|----------------------|----------------------|
| WSL x64 | 6.72 s / 1.55 s / 111 MB | **6.03 s / 0.68 s / 100 MB** |
| 10.0.0.1 | 5.23 s / 3.45 s / 110 MB | **3.84 s / 1.42 s / 98 MB** |
| A2 arm64 | 12.57 s / 14.55 s / 85 MB | **5.94 s / 5.17 s / 88 MB** |

Agent 的 R2R 收益非常明确：A2 启动 2.1 倍、CPU 少 65%；10.0.0.1 CPU 少 59%。稳态 CPU（A2 10 s 采样）R2R 约 240 ms，JIT 约 460 ms，R2R 仍低一半。

### 5.3 StarWeb 直连远程服务端

Windows 上让 StarWeb 直接接入 `http://star.newlifex.com:6600`，访问 `/cube/info`：

| 形态 | 启动 | 启动 CPU | 启动 RSS | 稳态 CPU（10 s） | 稳态 RSS |
|------|-----:|---------:|---------:|-----------------:|---------:|
| 框架依赖 JIT | 3.64 s | 5.55 s | 288 MB | 203 ms | 285 MB |
| 自包含 R2R | 2.43 s | 3.78 s | 292 MB | 219 ms | 304 MB |

远程接入没有改变结论：R2R 主要降低启动时间和首次 CPU，稳态 CPU/内存与 JIT 接近；远程心跳/埋点让稳态 CPU 比本地联合场景高一个量级（约 200 ms/10 s）。

## 6. 包大小

框架依赖，Linux/Windows：

| 组件 | JIT | R2R | 说明 |
|------|----:|----:|------|
| StarServer | 14 MB | 18~25 MB | Windows R2R 需 composite |
| StarWeb | 36 MB | 41~59 MB | Linux 普通 R2R 可用 |
| StarAgent | 6.9 MB | 12~14 MB | 自包含另计 |

包大小排第三；R2R 增加的 4~23 MB 相对于运行收益可接受，但 Windows 普通 R2R 的兼容问题比体积更值得关注。

## 7. 按场景选型

| 场景 | 推荐 | 备注 |
|------|------|------|
| StarAgent，生产机已装运行时 | **框架依赖 R2R** | 启动/CPU 收益最大，插件/反射不受限 |
| StarAgent，极弱设备且无外部插件 | AOT | 启动/内存最好，但插件不能动态加载；glibc 需匹配 |
| StarServer，长期运行、重启不频繁 | **框架依赖 JIT** | 稳态 CPU/内存与 R2R 接近，包小、部署简单 |
| StarServer，频繁重启/扩容、弱 CPU | **composite R2R** | Windows 必须 composite；Linux 普通 R2R 已验证 |
| StarWeb，门户启动体验重要 | **composite R2R** | 弱机启动提升 28%~38%，内存低约 10% |
| 需要现场插件/频繁调试 | JIT | R2R/AOT 都可能带来兼容问题，JIT 最稳 |
| 想“JIT 发布后再优化” | JIT + 动态 PGO | 不要找 NGEN；R2R 是发布时选项，不是目标机 NGEN |

## 8. 复现与注意事项

- 联合测试脚本：`joint.sh`（Linux）与 `joint-win.ps1`（Windows）在本次会话临时目录；核心命令为 `StarServer` → `/api`，`StarWeb` → `/cube/info`，`StarAgent -run -server http://127.0.0.1:6600`。
- A2 的 ARM64 `Microsoft.Data.Sqlite` 驱动版本较旧，不认识 `Busy Timeout/Journal Mode/Synchronous` 连接串关键字；StarWeb 默认配置已改为简单 SQLite 连接串，否则 ARM64 首次启动会失败。
- StarWeb 的 `IISServerOptions` 配置在 Linux 上会触发 `TypeLoadException`；已移除该 Windows/IIS 专用配置，Kestrel 的请求体限制保持不变。
- Windows 普通框架依赖 R2R 的 failfast 是实测结果；上线前请用 composite R2R 重新验证一次目标运行时版本。
- 本文的 A2/10.0.0.1/sh14 数据来自框架依赖和自包含两组；表格已标注生产口径，跨表不要混用。
