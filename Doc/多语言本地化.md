## 2. 词表文件

- `Stardust/Locales`
- `Stardust.Extensions/Locales`
- `Stardust.Server/Locales`
- `Stardust.Web/Locales`
- `Stardust.WebApi/Locales`
- `Stardust.Data/Locales`
- `StarAgent/Locales`
- `StarAgent.Mobile/Locales`
- `StarGateway/Locales`
- `Plugins/AgentExpansion/Locales`
- `Plugins/NetworkDetect/Locales`
- `DeployAgent/Locales`

- 文件名即 BCP 47 语言代码；英文是源文与兜底，**不需要** `en.yml`。
- 键为**英文原文**，必须与代码字符串逐字一致（含空格与标点）；占位符 `{0}` 与格式说明符 `{1:n0}` 必须与英文一致。
- 词表由 NewLife.Core 包内的源生成器在编译期读取并生成压缩语言表，NativeAOT 下同样可用。
- 全部运行时组件（SDK、服务端、管理端、代理、网关、插件、发布工具）的异常、日志、控制台与埋点标签已英文化，并提供中英文词条；其余语言暂以英文原文兜底，待翻译补齐后直接替换对应值即可。

日志语言与界面语言相互独立：`Localization.Culture` 控制异常与界面文案，`Localization.LogCulture` 控制日志与配置注释。日志直接写英文模板，由日志器按日志语言翻译；需要手动生成日志文本时用 `L.TLog`，异常文案用 `L.T`。带动态前缀的日志使用 `InfoPrefixed`/`ErrorPrefixed`，前缀在翻译之后拼接，避免前缀导致整串查表失败而回退英文。

## 3. 新增一条消息

1. 代码中写英文源文：`throw new XException("Session {0} is closed.", sessionId);`，日志直接写英文模板（`Logger.Format` 自动翻译）。
2. 在全部语言文件的同一位置补齐该键；暂未翻译的语言先写英文原文兜底，遗漏只会回退英文，不会编译失败。
3. 运行校验脚本确认键集合、占位符与格式说明符一致。

覆盖率报告由 `report-locales.ps1` 生成到 `Doc/多语言覆盖.md`，按语言与组件统计已翻译条目与唯一源文总数：

```powershell
pwsh -File report-locales.ps1
```

`Stardust.Tests` 中的 `LocaleConsistencyTests` 在 `dotnet test` 阶段执行同一套键集、占位符与格式说明符校验，并断言简体与繁体词表全部提供译文。

## 5. 运行环境与语言选择

目标语言来自 `CultureInfo.CurrentUICulture`（`Localization.Culture` 为空时），即操作系统的界面语言：Windows 取系统显示语言，Linux 取 `LANG`/`LC_MESSAGES`。`zh-CN` 命中 `zh-Hans`，`zh-TW` 命中 `zh-Hant`；没有对应词表的语言回退英文。

### 5.1 配置项固定语言

`Star.Language`（客户端 SDK，Star.json）与 `StarServer.Language`（服务端，数据库配置）可固定进程的界面与日志语言，取值如 `zh-Hans`、`zh-Hant`、`en`、`ja`。留空时跟随系统语言。星尘代理同样支持 `StarAgent.Language`，未配置时回退 `Star.Language`。

`StarLocalization.NormalizeCulture` 负责把 `zh-CN`、`de-AT`、`no`、`iw` 等写法归一化到词表语言，`StarLocalization.UseLanguage` 归一化后写入 `Localization.Culture` 与 `Localization.LogCulture`。

### 5.2 Web 宿主按请求识别语言

`StarServer.Language` 留空时，StarServer、StarWeb 与 StarWebApi 通过 `UseStardustLocalization` 注册请求语言中间件，优先级为查询串 `?lang=`、Cookie `.AspNet.Culture`、请求头 `Accept-Language`。中间件只修改 `CurrentUICulture`，不影响协议中的数字与日期格式；请求结束后还原。

识别期间日志与配置文件注释固定为宿主启动语言，避免同一日志文件随请求语言混杂。

.NET 6+ 在 Linux 上依赖 ICU（Debian/Ubuntu 包名通常为 `libicu`，Alpine 为 `icu-libs`）。缺少 ICU 时进程会在启动阶段失败，提示设置 `System.Globalization.Invariant`。无 ICU 的老旧/嵌入式系统可用环境变量降级：

```bash
# 直接运行
export DOTNET_SYSTEM_GLOBALIZATION_INVARIANT=1

# systemd 服务
sudo systemctl edit staragent
# [Service]
# Environment=DOTNET_SYSTEM_GLOBALIZATION_INVARIANT=1
sudo systemctl daemon-reload && sudo systemctl restart staragent
```

降级后进程照常运行，但只有英文，且不得显式设置 `Localization.Culture`（invariant 模式下创建具体区域性会抛 `CultureNotFoundException`）。环境变量优先级高于 `runtimeconfig.json`，升级部署时无需重新发布即可切换。

## 6. 批量翻译工作流

译文以英文源文为键批量写入，`apply-locales.js` 负责落到各组件词表：

```powershell
# entries.json: { "English key": { "ja": "译文", "de": "译文" }, ... }
node apply-locales.js entries.json Stardust/Locales Stardust.Server/Locales StarAgent/Locales ...
```

脚本先按各组件的 `zh-Hans.yml` 键集剔除多余键，再就地更新译文；词条未覆盖的语言保持英文占位。写入后依次执行 `check-locales.ps1` 与 `report-locales.ps1` 校验并刷新覆盖率。

## 7. 管理端界面文案

界面文案分两类，处理方式不同：

- **服务端返回的消息**（异常、API `message`、操作结果、部署历史）：已是英文源文并走 `L.T`，随请求语言输出，已覆盖。
- **界面静态文案**（控制器 `df.DisplayName`、实体 `[DisplayName]`、区域菜单、代理面板 `index.html`）：仍是中文源文。

第二类暂不改英文源文：当前引用的 NewLife.Cube 版本（6.15.2026.1018-beta1727）不调用 `Localization`，`[DisplayName]`、`[Description]` 与 `ListField.DisplayName` 原样渲染。此时把中文标签改成英文源文，会让中文界面直接显示英文，属于功能回退；Cube 主线已在 `ConfigController` 与 `CubeLocalization` 中实现 `L.T` 翻译，待发布后再统一切换并同步词表。

代理面板 `index.html` 为单文件内联页面，尚未接入前端词表；服务端接口消息已随请求语言本地化，页面静态文案的本地化需要前端字典或独立静态资源，单独排期。

不要在 csproj 里写死 `System.Globalization.Invariant`：它会让该项目所有平台、所有目标框架的构建永久失去多语言能力（StarAgent 2020 年为 linux-arm 无 ICU 环境加的开关即属此类，2026 年已移除）。
