## 2. 词表文件

- `Stardust/Locales`
- `Stardust.Extensions/Locales`
- `Stardust.Server/Locales`
- `Stardust.Web/Locales`
- `Stardust.WebApi/Locales`
- `Stardust.Data/Locales`
- `StarAgent/Locales`
- `StarAgent.Mobile/Locales`
- `StarGateway/Locales`
- `Plugins/AgentExpansion/Locales`
- `Plugins/NetworkDetect/Locales`
- `DeployAgent/Locales`

- 文件名即 BCP 47 语言代码；英文是源文与兜底，运行时消息**不需要** `en.yml`。界面元数据以中文为源文（菜单名、实体字段描述、自定义视图文案），需要在 `en.yml` 中登记英文译文，缺失时回退中文源文。
- 键为**英文原文**，必须与代码字符串逐字一致（含空格与标点）；占位符 `{0}` 与格式说明符 `{1:n0}` 必须与英文一致。
- 词表由 NewLife.Core 包内的源生成器在编译期读取并生成压缩语言表，NativeAOT 下同样可用。
- 全部运行时组件（SDK、服务端、管理端、代理、网关、插件、发布工具）的异常、日志、控制台、事件、命令返回结果、历史备注、埋点标签与配置项描述已英文化，并补齐 31 种语言译文（缺失或同形条目回退英文源文）。管理端自定义视图绑定与实体元数据是中文源文，通过 `L.T` 与 `en.yml` 输出英文，见第 7 节。告警通知（`AlarmService`、`RobotHelper` 与下线告警文案）面向中文运维群，仍为中文源文。

日志语言与界面语言相互独立：`Localization.Culture` 控制异常与界面文案，`Localization.LogCulture` 控制日志与配置注释；日志语言未显式设置时依次回退锁定语言、站点默认语言 `Localization.DefaultCulture` 与进程启动时的系统语言。日志直接写英文模板，由日志器按日志语言翻译；需要手动生成日志文本时用 `L.TLog`，异常文案用 `L.T`。带动态前缀的日志使用 `InfoPrefixed`/`ErrorPrefixed`，前缀在翻译之后拼接，避免前缀导致整串查表失败而回退英文。

日志与异常一律使用**格式字符串 + 参数**（`Log?.Info("Deleted {0}", path)`），不要用字符串插值（`$"Deleted {path}"`）：插值后模板已展开，无法再按原文查表。模板按整句匹配，参数本身不翻译；不要把英文状态词塞进 `{n}` 参数，应按语义拆成完整句子。

## 3. 新增一条消息

1. 代码中写英文源文：`throw new XException("Session {0} is closed.", sessionId);`，日志直接写英文模板（`Logger.Format` 自动翻译）。
2. 在全部语言文件的同一位置补齐该键；暂未翻译的语言先写英文原文兜底，遗漏只会回退英文，不会编译失败。
3. 运行校验脚本确认键集合、占位符与格式说明符一致。

CI 的 localization job 会执行同一组脚本。检查脚本覆盖抛异常、控制台与日志器（含 `log?.Warn` 这类可空调用）、`XTrace`、事件上报（`WriteInfoEvent`/`WriteEvent`）、自定义日志包装（`WriteError`/`WriteInfo`）以及 `return` 命令结果；只对字符串字面量判中文，中文标识符（如 `CommandStatus.错误`）不误报。孤儿键扫描同时读取 `.cs` 与 `.csproj`，程序集标题与描述作为词表 key 时不会误报。

覆盖率报告由 `report-locales.ps1` 生成到 `Doc/多语言覆盖.md`，按语言与组件统计已翻译条目与唯一源文总数：

```powershell
pwsh -File report-locales.ps1
```

`Stardust.Tests` 中的 `LocaleConsistencyTests` 在 `dotnet test` 阶段执行同一套键集、占位符与格式说明符校验，并断言简体与繁体词表全部提供译文。`StarPanelLocaleTests` 校验代理面板前端词表：31 份 `i18n/*.json` 键集一致，且 `index.html` 里的中文源文经词表替换后不再残留中文，新增面板文案忘记补词表会直接测试失败。`AgentPanelLocalizationTests` 验证代理面板的服务端配置文案、运行时长模板与鉴权消息在运行期确实能取到译文，并校验服务端本地化不改写内联脚本（避免译文撇号破坏脚本）。

## 5. 运行环境与语言选择

目标语言来自 `CultureInfo.CurrentUICulture`（`Localization.Culture` 为空时），即操作系统的界面语言：Windows 取系统显示语言，Linux 取 `LANG`/`LC_MESSAGES`。请求未声明受支持语言时先回退站点默认语言 `Setting.DefaultLanguage`，再回退系统语言。`zh-CN` 命中 `zh-Hans`，`zh-TW` 命中 `zh-Hant`；没有对应词表的语言回退英文。

### 5.1 配置项固定语言

界面语言统一由核心库基础配置 `NewLife.Setting`（`Config/Core.config`）决定，管理端「系统管理 → 系统设置」可直接选择，星尘不再单独提供平台设置项：

- `Language`：锁定界面与日志语言，设置后不再跟随请求语言。留空时跟随系统语言。
- `DefaultLanguage`：站点默认语言。请求没有受支持语言时作为界面兜底，同时作为日志、配置注释与后台线程的默认语言，**不锁定界面**。星尘平台还把它作为平台默认语言随登录/心跳下发给客户端（见 5.3）。
- 环境变量 `Language`、`DefaultLanguage` 优先于配置文件，Linux 上区分大小写。

`Star.Language`（客户端 SDK，Star.json）仍可固定客户端进程的界面与日志语言，优先级高于平台下发的默认语言。星尘代理与代理面板同样使用 Core 全局配置，不再读取 `StarAgent.Language`；面板右上角的选择器通过 `/api/SetLanguage` 写入该配置，留空恢复自动识别。Core 的语言码是 `zh-CN`、`en-US` 这类地区码，面板词表按 `zh-Hans`、`en` 命名，`i18n.js` 负责归一化后加载对应词表。

`StarLocalization.NormalizeCulture` 负责把 `zh-CN`、`de-AT`、`no`、`iw` 等写法归一化到词表语言；`StarLocalization.UseLanguage` 供客户端 SDK 固定进程语言（写入 `Localization.Culture` 与 `Localization.LogCulture`），平台下发的默认语言由 `StarClient.ApplyDefaultLanguage` 拦截，本地固定语言优先；代理与面板则走 Core 的 `Localization.SetLanguage`（由 `Setting.Save()` 自动应用）。

### 5.2 Web 宿主按请求识别语言

核心配置未固定语言时，StarServer、StarWeb 与 StarWebApi 通过 `UseStardustLocalization` 注册请求语言中间件，优先级为查询串 `?lang=`、Cookie `.AspNet.Culture`、请求头 `Accept-Language`。中间件只修改 `CurrentUICulture`，不影响协议中的数字与日期格式；请求结束后还原。`Localization.ForcedLanguage` 非空时直接跳过中间件，全进程使用配置语言。启动时先调用 `Setting.ApplyLanguage()` 把 `Language`/`DefaultLanguage`（含环境变量）应用到进程，保证对外服务前生效。

识别期间日志与配置文件注释固定为站点默认语言（未配置时回退宿主启动语言），避免同一日志文件随请求语言混杂。

界面语言与日志语言的分工：`Localization.Culture` 控制界面文案与异常提示，`Localization.LogCulture` 控制日志、配置注释与历史备注。管理端通常只需配置 `Setting.DefaultLanguage` 一项——界面按请求识别、没有受支持语言时用它兜底，日志与历史备注也用它；需要全站锁定时再配 `Setting.Language`，两者同时固定。因此同一台服务器上不同操作员可以使用不同界面语言，而落到库里的历史内容始终是服务器语言，不受触发者影响。

`Setting.DefaultLanguage` 同时承担日志语言：留空时日志依次回退 `Setting.Language` 与宿主启动语言；设置后**只影响日志、配置注释与历史备注**，界面语言照常走配置或请求识别。典型用法是界面按浏览器自动识别（多语言站点），日志固定为运维/开发者语言（同一次排障不会看到两三种语言的日志）。需要“界面锁定中文 + 日志英文”这种反向组合时，在代码中设置 `Localization.LogCulture`。

### 5.3 平台下发默认语言

星尘平台把核心配置 `Setting.DefaultLanguage` 作为平台默认语言，随登录响应与心跳响应的 `DefaultLanguage` 字段下发（`DefaultDeviceService` 自动填充，旧服务端不下发时客户端保持本机配置）。客户端 `ClientBase` 收到后保存到本机核心配置 `Setting.DefaultLanguage`，下次启动在首次登录之前即生效；进程内优先级为**本地固定语言 > 平台默认语言 > 系统语言**。

- 服务端：修改 `Core.config` 的 `DefaultLanguage`（或设置环境变量）并重启，即对全部新登录与心跳的客户端生效。
- 客户端：`Star.Language`（Star.json）非空时视为本地固定语言，平台默认语言不再改写界面与日志，也不写入本机配置，避免下次启动被平台语言顶掉。
- 代理面板：核心配置 `Language`（面板右上角固定）→ 浏览器 `Accept-Language` → 平台默认语言 → 系统 `LANG`/`LC_ALL`。
- 自动识别的界面语言按请求级生效，日志语言固定为默认语言，两者互不影响。

.NET 6+ 在 Linux 上依赖 ICU（Debian/Ubuntu 包名通常为 `libicu`，Alpine 为 `icu-libs`）。缺少 ICU 时进程会在启动阶段失败，提示设置 `System.Globalization.Invariant`。无 ICU 的老旧/嵌入式系统可用环境变量降级：

```bash
# 直接运行
export DOTNET_SYSTEM_GLOBALIZATION_INVARIANT=1

# systemd 服务
sudo systemctl edit staragent
# [Service]
# Environment=DOTNET_SYSTEM_GLOBALIZATION_INVARIANT=1
sudo systemctl daemon-reload && sudo systemctl restart staragent
```

降级后进程照常运行，但托管侧拿不到具体区域性：`Localization.Culture`/`LogCulture` 无法设置（invariant 模式下创建具体区域性会抛 `CultureNotFoundException`，设置入口会捕获），日志、配置注释与异常提示回落英文。**界面文案不受影响**——各组件的文案都来自自己的词表，翻译与 ICU 无关；StarAgent 面板判定语言时依次读核心配置 `Setting.Language`、请求头 `Accept-Language`、平台默认语言 `Setting.DefaultLanguage`、系统环境变量 `LC_ALL`/`LC_MESSAGES`/`LANG`，全程只做字符串比对，实测在关闭 ICU 的进程里带中文请求头仍返回中文界面（见 [NODE-StarAgent架构](NODE-StarAgent架构.md) 第 8 节）。

环境变量优先级高于 `runtimeconfig.json`，升级部署时无需重新发布即可切换。星尘代理的 Linux 发布包直接在 `runtimeconfig.json` 里写着 `System.Globalization.Invariant=true`（省下 ICU 三个共享库约 8 MB），这比靠环境变量注入更可靠：**有些嵌入式系统压根没装 ICU**，靠环境变量注入时进程可能在注入生效前就已经启动失败；需要中文日志的部署在服务单元里显式设 `Environment=DOTNET_SYSTEM_GLOBALIZATION_INVARIANT=0` 即可覆盖该默认值。

## 6. 批量翻译工作流

译文以英文源文为键批量写入，`apply-locales.js` 负责落到各组件词表：

```powershell
# entries.json: { "English key": { "ja": "译文", "de": "译文" }, ... }
node apply-locales.js entries.json Stardust/Locales Stardust.Server/Locales StarAgent/Locales ...

# 统计某语言仍为英文占位的键
node apply-locales.js --missing es
```

脚本先按各组件的 `zh-Hans.yml` 键集剔除多余键，再就地更新译文；词条未覆盖的语言保持英文占位。写入后依次执行 `check-locales.ps1` 与 `report-locales.ps1` 校验并刷新覆盖率。

界面元数据（菜单名、实体字段描述，键为中文源文）走同一脚本的元数据模式：

```powershell
# 1) 收集键清单（全部模型 XML + 控制器/视图中的 DisplayName/Description/L.T 文案）
$models = (Get-ChildItem Stardust.Data -Recurse -Filter Model.xml | Where-Object { $_.FullName -notmatch '\\(obj|bin)\\' }).FullName
./collect-metadata-keys.ps1 -Model $models -Output Stardust.Data/Locales/metadata-keys.json
./collect-metadata-keys.ps1 -SourceDir Stardust.Web -Output Stardust.Web/Locales/metadata-keys.json
# Stardust.Server 的 metadata-keys.json 手工维护：键是配置项中文摘要首句（XML 注释），不是特性

# 2) 写入译文（元数据键免于 zh-Hans 键集裁剪，单独成节）
node apply-locales.js --metadata Stardust.Data/Locales/metadata-keys.json --section "# 界面元数据词条" entries.json Stardust.Data/Locales

# 3) 校验（`-MetadataKeys` 允许元数据键只出现在部分语言）
pwsh -File check-locales.ps1 -LocaleDir Stardust.Data/Locales -SourceDir Stardust.Data -MetadataKeys Stardust.Data/Locales/metadata-keys.json
```

### 6.1 与英文同形的词条

少数条目在目标语言中本就与英文同形，属正确译文而非漏翻，`report-locales.ps1` 会将其计为未翻译：Hash、Commit、Status、Server、Site、Repository、Branch、OOM score 等技术通用词，以及 NAT proxy、Process ID 这类缩写加借词的组合。`identical.allow.json` 按语言登记后由严格模式放行。各语言的实时覆盖率以 `Doc/多语言覆盖.md` 为准：运行时消息接近全覆盖，界面元数据以中文为源文、英文优先补齐，其余语言按需增量翻译，缺失回退中文源文，不影响编译与运行。

## 7. 管理端界面文案

界面文案分两类，处理方式不同：

- **服务端返回的消息**（异常、API `message`、事件、命令返回结果、历史备注）：已是英文源文并走 `L.T` 或日志翻译，随请求语言输出，已覆盖。代理面板的配置项分组、字段名、说明、运行时长（`FormatUptime`）与鉴权/服务管理器错误同样由 `StarApi` 用 `L.T` 输出，语言由 Core 全局配置决定。
- **历史操作名**（应用历史/节点历史的 `Action`）：数据库只保存英文规范键（`HistoryAction` 常量），写入方不再翻译动作名，避免同一条操作因写入进程语言不同在库里出现多种文本；管理端列表、详情链接与看板经 `HistoryAction.Localize` 按当前界面语言展示，旧数据中的中文操作名由 `HistoryAction.Normalize` 归一化后再翻译。`Action` 是筛选与分组的枚举维度，因此不存翻译文本，服务器界面语言不影响其存储与查询。
- **历史内容**（应用历史/节点历史的 `Remark`）：它是事件的文字快照，写入时用 `L.TLog` 跟随服务器日志语言（`Localization.LogCulture`），不随触发者的界面语言变化，保证同一条事件在不同操作员触发时记录一致。
- **界面静态文案与 Cube 操作结果**（控制器 `df.DisplayName`、实体 `[DisplayName]`、区域菜单、`JsonRefresh`/`Alert` 提示）：仍是中文源文，与第二类一并处理。列表字段的单元格文字模板（如 `{Name}`）必须写在 `ListField.Text`，不能写 `DisplayName`——本地化会把它当列头输出，表头会直接显示 `{Name}`。

当前引用的 NewLife.Cube（6.16.2026.1027）已接入编译期词表：`ConfigController` 经 `DataField.Localize` 翻译配置项，实体列表与菜单名经 `L.T` 翻译，`[DisplayName]`/`[Description]` 与 `ListField.DisplayName` 随请求语言输出。Stardust 侧的界面文案因此分三种处理：

- **实体与控制器元数据**：保持中文源文，中文 key 写在 `Stardust.Data/Locales`、`Stardust.Web/Locales`、`Stardust.Server/Locales` 的 `metadata-keys.json`，英文译文写入同目录的 `en.yml`，其余 30 种语言写在同一 `*.yml`；缺失时回退中文源文。简体中文直接返回源文，不进入 `zh-Hans.yml`。
- **自定义视图文案**：`.cshtml` 中的中文界面文案用 `L.T("...")` 包裹，英文译文同样进入 `en.yml`；JS 内的提示拼接使用 `'@L.T("...")'`，带动态参数时用 `L.T("... {0} ...", value)`。
- **配置页描述**：`StarServerSetting` 的 `[Description]` 是英文源文，译文在 `Stardust.Server/Locales`。StarWeb 与 StarWebApi 通过 `Compile Include` 复用源码但不加载 Server 程序集，因此 Web/WebApi 的 `Locales` 同步保留一份 Server 词条（`merge-server-locales` 方式），否则配置页永远显示英文。
- **语言选择**：统一使用核心库基础配置 `NewLife.Setting`（`Core.config`）：`Language` 锁定界面与日志，`DefaultLanguage` 作为界面兜底、日志语言与平台下发语言；平台设置不再提供「界面语言」项；调用 `UseStardustLocalization` 时若 `Localization.ForcedLanguage` 非空则直接跳过请求语言中间件。

上游仍待办：Cube 内置的登录页、仪表盘部件、`ListField.Text`（如 `TraceUrl` 的「追踪」文字）与部分按钮文案未接入 `L.T` 或缺少 en 词条。星尘侧已用 `LocalizedTraceUrl` 扩展替换追踪链接文字，其余属于 NewLife.Cube 仓库范围；E2E 断言已兼容中英文两种站点名。

工具链：`collect-metadata-keys.ps1` 收集键（支持 `metadata-extra.json` 增量补 `L.T` 标签）、`check-locales.ps1 -MetadataKeys` 校验（元数据键可部分缺失、免孤儿键检查）、`apply-locales.js --metadata --section "# 界面元数据词条"` 写入、`report-locales.ps1` 第 3 节统计元数据覆盖率。C# 中直接以中文源文调用 `L.T` 的界面文案（如列表链接文字）在行尾标注 `// ui`，`check-english-exceptions.ps1` 会豁免该行，避免把既有元数据机制误判为未英文化。

告警通知（`AlarmService`、`RobotHelper` 与节点/应用下线告警）面向中文运维群，保持中文源文，不参与运行时消息检查。

### 7.1 代理面板前端词表

`StarAgent/WebPanel/wwwroot/index.html` 保持中文源文，`StarPanel` 重写 `WriteIndex`，在输出 HTML 前用 `UiLocalization.GetDictionary` 的词表按当前语言对源文做最长匹配替换，简体中文直接返回源文；因此登录页等静态文案在浏览器收到 HTML 时已是目标语言。替换只作用于脚本与样式之外的标记——基类 `UiLocalization` 会连内联脚本一起替换，法语、乌克兰语译文中的撇号会破坏单引号字符串导致脚本语法错误。脚本内的中文由同目录的 `i18n.js` 负责：它把 DOM 文本节点、`placeholder`、`title` 与 `aria-label` 按词表替换，`MutationObserver` 覆盖动态渲染。词表是 `wwwroot/i18n/<语言>.json`（31 份，键为中文源文），随 wwwroot 作为嵌入资源打进程序集，由内嵌静态文件服务按 `/i18n/<语言>.json` 提供，服务端与浏览器端共用同一份词表。

`i18n.js` 启动时读取 `/api/Languages` 拿到语言清单与语言状态：有固定语言（`current`）时界面跟随它，未固定时跟随服务端实际生效语言（`effective`），接口不可用时才退回 `navigator.language`，并复用同一套归一化规则（`zh-CN` 映射到 `zh-Hans`）。下拉项显示服务端返回名称括号内的本地名（`德语 (Deutsch)` → `Deutsch`），避免中文前缀混入其他语言的界面。面板右上角的语言选择器调用 `/api/SetLanguage` 把选择写入 Core 全局配置 `NewLife.Setting.Language`（留空恢复自动识别），写入后重载页面；阿拉伯语、波斯语、希伯来语同时把根元素方向设为 `rtl`。`/api/SetLanguage` 需要登录，因此登录页固定跟随服务端语言，登录后才能切换。

匹配规则：文本节点整串命中词表优先；否则按最长短语多轮替换，直到没有可命中的词条，因此 `确定要重启服务吗？重启后服务将自动恢复。` 这类拼句会被整体译出。单字词条只在两侧都不是汉字时替换，避免误伤。`placeholder`、`title` 与 `aria-label` 同样走词表翻译。需要拼接动态值或 HTML 的句子用 `StarI18N.t()` 显式翻译后再插入，占位符写成 `{0}`，例如删除确认弹窗的 `确定要删除子服务 {0} 吗？`。

接口请求不再携带语言参数：固定语言写入 `NewLife.Setting.Language` 后由 `Localization` 进程级生效，服务端消息、接口错误与日志保持一致。面板不按请求头识别语言，未固定时所有请求都使用进程的界面语言，因此 `i18n.js` 以 `/api/Languages` 的 `effective` 为准，而不是浏览器语言，避免界面与服务端消息不一致。`StarApi` 不再自行解析语言。

新增面板文案时先改 `index.html` 的中文源文，再把该源文补进 31 份词表 JSON；`Stardust.Tests` 的 `StarPanelLocaleTests` 会校验遗漏。面板词表与 `StarAgent/Locales` 的后端词表互相独立：后者只用于服务端生成的消息（配置项文案、运行时长等），不参与 `index.html` 中文源文的替换。

不要在 csproj 里写死 `System.Globalization.Invariant`：它会让该项目所有平台、所有目标框架的构建永久失去多语言能力（StarAgent 2020 年为 linux-arm 无 ICU 环境加的开关即属此类，2026 年已移除）。

## 8. 程序集与包元数据

跟随 NewLife.Core v12 规范，程序集标题与描述采用「英文源文 + 词表 + 展示层翻译」：

- csproj 的 `AssemblyTitle` 与 `Description` 使用**英文源文**，同一字符串作为 key 写入本程序集 `Locales/*.yml`：中文给译文，其余语言同样写出译文，缺失时回退英文源文。
- 展示点用 `L.T(value)` 翻译：NewLife.Agent 的 `DisplayTitle`/`DisplayDescription` 已内置（控制台标题、`-status` 输出、面板、Windows SCM/systemd 注册），`DeployAgent` 控制台描述自行调用。服务名不翻译，用户配置的 `DisplayName` 同样走 `L.T`。
- `check-locales.ps1` 的孤儿键扫描已覆盖 `.csproj`，元数据 key 不会被误判。
- NuGet 包另有 `<PackageDescription>` 承接中英双语描述；`Description` 保持纯英文供反射使用，`PackageTags` 可保留中英关键词。

`StarAgent/MyService` 与 `DeployAgent/DeployService` 的 `DisplayName`/`Description` 与各自 csproj 保持同一英文串，安装注册和面板显示随语言切换。

插件与测试的 `[DisplayName]`/`[Description]` 属表结构或插件元数据，保持项目母语，不进入运行时消息检查；确需翻译时按 Core 规范的元数据 key 机制单独登记。

配置项 `[Description]` 已改为英文源文，同一字符串作为 key 写入各组件 `Locales/*.yml` 并补齐 31 种语言译文；Core 在读取与保存配置时按 `Localization.LogCulture` 查表输出，缺失回退英文源文。实体与控制器元数据（菜单名、字段描述）仍保持中文源文，走第 7 节的界面元数据词条：`Stardust.Data/Locales`、`Stardust.Web/Locales` 与 `Stardust.Server/Locales` 的 `metadata-keys.json` 登记中文源文键，英文译文写入同目录 `en.yml`，其余语言的译文写在同一 `Locales` 目录的 `*.yml` 中。

`Installer`、`StarAgentTool`、`StarAgent.Android`、`StarAgent.iOS`、`MySqlAgent` 未纳入解决方案的词表体系，暂保留中文 `AssemblyTitle`/`Description`；它们不参与服务注册与面板展示。
